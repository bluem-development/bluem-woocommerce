# BLUEM-WOOCOMMERCE-3H investigation

Investigated on 2026-10-10. No deployment, publication, version bump, or dependency update performed.

## Confirmed evidence

Authenticated read-only access through the Sentry skill retrieved the [issue](https://bluem.sentry.io/issues/7766198408/), event `bb09d3b1453545bc83dc57377dd1a401`, and available surrounding events. There is one occurrence, at 2026-10-01 15:20:23 UTC, production, `bluem@1.6.5`, SDK 4.29.0. The full event has only one synthetic fatal frame, at `src/Support/BluemComposerDependencyVersion.php:21`, the `json_decode` operation. It has no caller stack, request context, PHP version, or memory limit. The allocated 50,855,936 bytes and attempted 20,480 bytes establish neither the configured memory limit nor the initial source of memory pressure.

The production 1.6.5 issue search over the available 14-day window returned this issue and a pre-existing missing-log-file copy warning. That warning's available events were September 30, October 7, and October 8, with no adjacent October 1 event or evidence connecting it to this failure. Request correlation is unavailable. Sentry intentionally removes request, breadcrumbs, user, and runtime context in `sanitizeEvent`; fetching the full event cannot recover them.

The checkout is the 1.6.5 release commit (`298fbee`). Before this fix, the reader and its Sentry caller were identical to tag `1.6.5`. Extraction commit `bd0ccca` (July 29) retained the pre-existing full-lockfile decoding behavior, replacing an `array_filter` with a loop. Commit `0934d43` (August 17) added dependency detection during Sentry initialization, extending it to ordinary plugin loads. The lockfile includes development metadata even though production vendor installs omit development packages; its size here is 272,127 bytes.

Call paths:

- `bluem.php` invokes `BluemSentry::initialize()` during plugin load, after requiring the vendor autoloader. Initialization loads diagnostic tags once if a DSN is enabled.
- `bluem_get_composer_dependency_version()` constructs another reader for admin home, activation notification, and support-report environment collection.
- `bluem_error_report_email()` collects the environment before calling `captureReport()`. That method invokes initialization again, but Sentry sets its initialized guard before SDK initialization and tag collection.

The old reader decoded the whole lockfile on every call and retained no cache. Code-path review found no reader-to-logging, reader-to-Sentry, or recursive autoload edge. It did not leak memory across repeated calls in the standalone harness. Other request allocations and unusually large deployed metadata remain possible contributors, without evidence to rank them.

## Reproduction and fix

A standalone PHP 8.4.24 harness loads only the reader, allocates controlled unrelated padding, leaves roughly 512 KiB in the current allocator, and sets a limit that prevents another allocator arena. This reproduces a fatal at old line 21 with an attempted 20,480-byte allocation. It demonstrates that pre-existing request pressure plus this reader's allocation spike can cause failure. It does not reproduce the production request or host exhaustion: the harness reports PHP's explicit `Allowed memory size ... exhausted`, whereas production reported `Out of memory ...`.

The fix reads the plugin's own `vendor/composer/installed.php`, generated by Composer alongside its required autoloader and retained by production packaging. It uses `pretty_version` to preserve human-readable dependency reporting, caches a compact version map per metadata path for the request, and sets a reentrancy guard before reading. Both direct callers now pass this path. It does not consult the global Composer registry, which can contain another plugin's version of the dependency.

Missing/unreadable metadata or absent version data returns null, preserving the callers' existing false/unknown/omitted-tag behavior. There is deliberately no lockfile fallback or logging: decoding the lockfile on an error-reporting path would reintroduce the demonstrated spike. Normal Composer-built packages retain dependency reporting (`2.7.3` here). The constructor now accepts installed metadata rather than a lockfile; all repository callers are updated. The top-level Composer files remain packaged. No supported PHP version or WordPress/WooCommerce interface changes.

Measured with CLI OPcache disabled:

| Reader | First-call temporary peak increase | Retained after first call | Growth over 1,000 further calls |
| --- | ---: | ---: | ---: |
| Old, actual lockfile | 1,317,592 bytes (unconstrained); fatal in constrained run | approximately zero | no accumulating growth |
| New, full development installed metadata (41,770 bytes) | 300,832 bytes | 17,752 bytes | 0 bytes |
| New, no-dev installed metadata (5,606 bytes) | 61,072 bytes | 2,696 bytes | 0 bytes |
| New, missing metadata | 456 bytes | 456 bytes | 0 bytes |

These are operation-level measurements, not whole-request WordPress/Sentry memory totals. Even small allocations cannot guarantee survival in a process with no available memory.

Reproduce from the repository root:

```sh
git show 1.6.5:src/Support/BluemComposerDependencyVersion.php > /tmp/bluem-version-old.php
php -d opcache.enable_cli=0 tests/Fixtures/composer-version-memory.php /tmp/bluem-version-old.php composer.lock
# Expected: exit 255, fatal at line 21.
php -d opcache.enable_cli=0 tests/Fixtures/composer-version-memory.php src/Support/BluemComposerDependencyVersion.php vendor/composer/installed.php
# Expected: success, version=2.7.3, repeated_delta=0.
```

Production measurements used a separate temporary `composer install --no-dev --no-plugins --no-scripts` from the unchanged lockfile. No production package was staged.

To confirm the production diagnosis, obtain the affected host's PHP version/SAPI, effective request `memory_limit`, PHP/web-server logs, OS/container/process memory limits and OOM records, request route/task and active plugin set, and the deployed lockfile/installed metadata sizes and versions. In staging, measure used/allocated/peak memory before plugin load, before and after SDK initialization, and before/after dependency detection with the same plugin set and request. Keep diagnostics small and local; do not send request payloads or recursively report allocation errors. Missing diagnostic tags are consistent with failure during initialization before tags were applied, but do not prove that caller.

## PR-ready summary and rollout

**Title:** Reduce memory used by runtime dependency-version diagnostics

Dependency detection decodes the full Composer lockfile during Sentry initialization and support reporting. Under controlled existing memory pressure, release 1.6.5 fails at that decode. Read the plugin's local Composer installed metadata once per request instead, retaining dependency versions and avoiding cross-plugin registry conflicts. Missing metadata returns unknown without logging or a lockfile fallback. The no-dev first-call peak falls from approximately 1.26 MiB to 60 KiB in the harness; 1,000 repeated calls add no memory. The production source of memory pressure remains unconfirmed.

Validation: PHP 8.4 Unit suite (142 tests / 410 assertions), lint, Composer validation/platform checks, diff check, and constrained-memory old/new reproduction.

Before a later reviewed release, confirm `vendor/composer/installed.php` is present in the packaged artifact and verify version reporting on a staging WordPress/WooCommerce site. Roll out to a small group first, smoke-check admin status, checkout/callbacks, support-report version fields, and Sentry initialization. Monitor 3H and all fatal/OOM issues by the new release, including failures that move to another location, and verify dependency-version tags remain populated. If OOM persists, investigate host/request memory pressure with the missing evidence above; raising memory limits is not this fix. No rollout or publication is authorized by this investigation.
